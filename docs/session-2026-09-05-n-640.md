# Session record: zero detections at 640

**5–6 September 2026 · `arg-bolts-4` · pod spend ≈ $5.50 · 9 compiles · 159 tests passing · nothing committed**

**`n` at 640 works, and the cause was one number.** Not the class-head bit width, not the
calibration set, not the input size — the NMS score floor baked into the `.hef`. Rebuilt with
`HEF_CONF=0.0001` instead of `0.001`, everything else identical, it scores **0.7715 mAP50
(99.3% of `best.pt`) at 24.4 ms** — inside the 33 ms frame at native resolution.

The model was never dead. It was being thresholded on-chip before the host saw a proposal.

Written to be picked up cold.

## 2. What was tested, in order

### H1 — "the class head lost its scores to 8-bit, fix it with `--a16-cls`" → **falsified**

The session's opening premise, carried over from a 7-class model where a16 genuinely helped.
Four `.hef` rebuilt on a rented 4090.

It **did** fix `s`: 0.0313 → 0.6549. It made `n` **worse**: 0.0995 → 0.0000.

A controlled rerun settled it — fresh a8 and fresh a16, same session, same host, same
calibration, gated back to back:

| `n` @ 640 | `.hef` bytes | mAP50 | recall |
|---|---:|---:|---:|
| a8 (no flag) | 7,543,838 | 0.0000 | 0.0000 |
| a16 (`--a16-cls`) | 7,557,958 | 0.0000 | 0.0010 |

The flag is **not** the variable for `n`. Verified the flag did not leak into the control
arm (`grep -c "a16 class head" dfc_a8.log` = 0).

### H2 — "INT8 calibration is class-skewed, balance it" → **falsified**

Ultralytics slices calibration as `im_files[: round(len × fraction)]` off a **sorted** list
(`ultralytics/data/base.py:177,183`) — a head slice, not a sample. On this dataset that gave
bolt 70.0 / nut 20.6 / screw 3.5 / washer 5.9 percent of boxes, against a true
60.9 / 20.7 / 8.6 / 9.8. Per-class INT8 damage rank-ordered *exactly* with those shares,
which looked conclusive.

Balancing it (seeded shuffle via symlink tree — deviation from the full split fell 9.1 pp → 0.4 pp)
made it **17% worse**:

| `n` litert int8 | mAP50 | bolt | nut | screw | washer |
|---|---:|---:|---:|---:|---:|
| sorted head slice (pod-built) | 0.4170 | 0.734 | 0.544 | 0.128 | 0.260 |
| sorted head slice (Mac-built, control) | **0.4170** | 0.735 | 0.547 | 0.128 | 0.258 |
| seeded shuffle | 0.3446 | 0.511 | 0.504 | **0.095** | 0.270 |

`screw` got **worse** with 2.4× the representation — the theory's central prediction, inverted.

**Mechanism, in hindsight:** INT8 has 256 levels either way. A homogeneous slice keeps each
layer's activation range narrow and its steps fine; a shuffled one spans every lighting
condition and scale in the dataset and widens the ranges. Representative calibration is the
standard advice and it loses here.

Reverted. The measurement is now in `calib_yaml()`'s docstring and the `HEF_FRACTION` bullet
of `docs/autorun-runpod-e2e.md`, with an explicit "do not fix this without re-measuring".

Side result worth keeping: the pod-built and Mac-built controls agree to **four significant
figures**, so the gate is reproducible across hosts. An hour of Mac time can settle this class
of question without renting anything.

### H3 — "something specific to `yolo11n` at 640" → **partly right, wrong mechanism**

480 does work (0.7159, 16.6 ms — see below). But so does 640, once the baked NMS floor is
lowered. Input size was a symptom, not the cause.

### H4 — "the baked `nms_scores_th` is discarding everything on-chip" → **CONFIRMED**

| `n` @ 640, identical in every other respect | mAP50 | max score | median | FPS |
|---|---:|---:|---:|---:|
| `HEF_CONF=0.001` | **0.0000** | 0.007 | 25.9 ms | 38.6 |
| `HEF_CONF=0.0001` | **0.7715** | **0.909** | 24.4 ms | 40.9 |

Per class at 0.0001: bolt 0.960, nut 0.867, screw 0.626, washer 0.634. Precision 0.8595,
recall 0.6845.

**The scores are not compressed.** Max 0.909 against `ncnn fp16`'s 0.919 on the same image —
normal, usable confidences. So this is directly deployable: filter host-side at whatever
threshold you want, `--conf 0.25` behaves as expected. No rescaling, no host-side decoder.

The earlier "~100× score compression" reading came from the 0.001-baked a16 build and was an
artifact of the floor, not a property of the model.

**Still unexplained:** why a 0.001 floor annihilates `yolo11n` at 640 while `yolo11s` survives
it at the same setting. That is now a curiosity, not a blocker.

#### Original H3 evidence (kept — it is what led to H4)

**`n` at 480 works.** Same weights, same calibration, same toolchain, same pod, same 200-image
gate — only the input size differs.

**This is the first arg-bolts 480 measurement that has ever been taken.** The plan justified V1
by citing `RESULT.md`'s "480 lost only 0.6%" — that figure is `poc-v2-480` on `fod-a-3k`, a
different model and dataset, and says nothing about arg-bolts. An arg-bolts 480 `.hef` does exist
(`artifacts/arg-bolts-4-480-100e/bench_int8_hailo_model`, built 3 Sept) but was **never accuracy
tested**, and is baked at conf 0.25 so it could not have been scored comparably. The right
conclusion was reached from a misread citation.

| `n` hailo int8 | mAP50 | bolt | nut | screw | washer | median | FPS |
|---|---:|---:|---:|---:|---:|---:|---:|
| **@ 480** | **0.7159** | 0.948 | 0.824 | 0.571 | 0.521 | **16.6 ms** | **60.3** |
| @ 640 | 0.0000 | 0.000 | 0.000 | 0.000 | 0.000 | 25.9 ms | 38.6 |

That is the answer to the practical problem: 92% of `best.pt`'s accuracy at half the 33 ms frame
budget. p95 17.0 ms, drift +0.5%, governor `performance`.

The failure is **input-size-specific to `yolo11n` on this toolchain**, not a flag, not the
calibration, not the weights. Why 640 specifically kills it is still unexplained — V2/V3/V4 below
are now research rather than blockers.

**What 640 has eliminated**, for whoever picks the research up:

| observation | eliminates |
|---|---|
| `n` `best.pt` 0.7769 on the Pi | the weights |
| `n` `ncnn fp16` 0.777 | export path, eval subset, the gate itself |
| `n` `litert int8` 0.417 — degraded but alive | INT8 in general |
| `n` @ **480** = 0.7159 this session | architecture, toolchain, class count, weights |
| (`RESULT.md`'s −0.6% is **`poc-v2-480`**, a different model on `fod-a-3k`) | — cites nothing about arg-bolts |
| `s` @ 640 = 0.6549, same pipeline | calibration, DFC, board, flags |
| fresh a8 == a16 == 0.0000 | `--a16-cls` |
| `n`/`s` `nms_config.json` identical in structure | reg/cls layer swap |
| both multi-context (3 each) | context count |

**Leading suspicion, untested:** the `.hef` bakes `nms_scores_th: 0.001` and runs NMS on-chip.
The a16 build returned 2 proposals at max 0.0071 where `litert` returned 125 at max 0.878 —
~100× score compression. Compress a little further and everything falls under the floor before
the host ever sees it. The fresh a8 returns **zero** proposals even at conf 0.0001. V2 tests this
directly.

V1 passed and settled the shipping question. V2-V4 still run — they are now research into *why*
640 fails, not attempts to unblock anything.

| Variant | Change | A pass would mean |
|---|---|---|
| ~~**V1 · 480**~~ | input size only | **PASSED — 0.7159 mAP50, 16.6 ms, 60.3 FPS.** Ships. |

| **V3 · opt-level 4** | DFC level 2 → 4 | Bias correction / AdaRound recover the range Ultralytics' hardcoded level 2 loses |

If V2-V4 all return zero, the conclusion is that `yolo11n` at 640 does not quantize on this
toolchain. That is now an acceptable answer rather than a dead end, because 480 ships.

## 5. Two bugs found and fixed

**LiteRT INT8 was OOMing, not failing to convert.** `exit 137` (SIGKILL) against a **31 GB**
container limit that `free` hides by reporting the 251 GB host. `export_litert()` never plumbed
`fraction`, so LiteRT calibrated on the whole 8,891-image train split at 640 — 3.3× what hailo
used. The exit code was being truncated out of the manifest by a 1500-char window, which is why
it read as a converter bug.

**`n`'s compile log revealed two things**, neither the hoped-for diagnostic:

- `Single context flow failed: Recoverable single context error` — `n` cannot fit one context and
  is split into 3, so weights reload mid-inference.
- **Layer Noise Analysis prints only a completion time at default verbosity.** The per-layer SNR
  table is *not* in the default output. Getting it needs a model-script directive — which the new
  `model_script_patch()` seam now makes cheap to add.

## 6b. What optimization level 4 revealed (V3, still running)

Level 4 adds algorithms level 2 skips entirely — and its log is the most informative this
toolchain has produced:

```
Statistics Collector    64 entries
Adaround              1024 entries, up to 18.45 GB scratch
bias correction         64 entries
[QAT finetune]        2667 entries
```

**Different stages use different amounts of data.** Only the finetune sees all 2,667, so
`HEF_FRACTION` matters far less than the "2667 calibration images" warning implies. Another
reason the calibration-balancing experiment (H2) moved in an unexpected direction.

**And the quantizer names the class head as a problem:**

```
No shifts available for layer best/conv54/conv_op, using max shift instead. delta=0.7873
No shifts available for layer best/conv65/conv_op, using max shift instead. delta=1.1631
No shifts available for layer best/conv80/conv_op, using max shift instead. delta=0.8451
```

`conv54`, `conv65`, `conv80` are exactly the three class convs. The quantizer could not find a
usable scale shift for them and fell back to max shift. That is the closest thing to a per-layer
diagnostic seen all session. **Worth checking whether the same lines appear in `s`'s log** —
`s` survives the 0.001 floor that kills `n`, and this may be why.

**AdaRound is per-layer**, which is why V3 shows dozens of training runs: one reconstruction
problem per conv, ~4 min each across ~70 convs. Budget **4–5 hours**, not the ~35 min the other
variants took. If you want bias correction without that cost, use `--opt-level 3`.

## 7. Things that will bite again

**Speed-check the pod before setup.** One host delivered **440 KB/s** from PyPI — eight hours for
the venv. Its replacement did **15.4 MB/s**. One curl costs seconds:

```bash
curl -sL -o /dev/null -w "%{speed_download} B/s\n" <a real PyPI wheel URL>
```

- **Community cloud gives no TCP port 22** — no rsync, no log retrieval. Secure cloud whenever
  artifacts must come back.
- **Never wait on `pgrep -f <script>`.** It matches the waiter's own command line and spins
  forever. Wait on a PID. This cost time four times in one day.
- **`${var:+VAR=1}` is not a conditional env prefix.** Bash resolves assignment-vs-command at
  parse time, so the expansion becomes the command name. It silently killed a compile.
- **One Hailo device session per gate.** `predict()` then `val()` on the same model raises
  `HAILO_OUT_OF_PHYSICAL_DEVICES`. Run `val()` alone.
- **Gate every model, not one of a pair.** Stopping after `n` scored zero nearly buried the fact
  that `s` had been fixed.
- **Gate before compiling.** `litert int8` shares the calibration path, runs on the Mac in ~20 min,
  and killed H2 before any pod time was spent on it.

## Reproducing any of this

```bash
# Pi -- the accuracy gate (the check that was missing all along)
~/.local/bin/uv run fodcv-bench --run arg-bolts-4-n-640 --imgsz 640 \
  --formats hailo litert ncnn --precisions int8 fp16 --val-max 200

# Pi -- one variant against its own best.pt on the same 200 images
~/.local/bin/uv run python -c "
from ultralytics import YOLO
m = YOLO('artifacts/arg-bolts-4-n-640/<variant_dir>', task='detect')
r = m.val(data='runs/bench_pi/val_subset_200/data.yaml', imgsz=640,
          conf=0.001, device='cpu', verbose=False, plots=False)
print(r.box.map50, r.box.map, r.box.mr)"

# Pi -- latency, CPU format first so drift control is not the accelerator warming up
taskset -c 0-3 ~/.local/bin/uv run fodcv-bench --run arg-bolts-4-n-640 --imgsz 640 \
  --formats ncnn hailo --threads 4 --no-val --cooldown 120 --temp-target 66
```

Board conditions first or the latency is fiction (`README.md` § five things): governor
`performance` on all four cores, `sudo systemctl stop lightdm`, `--cooldown 120 --temp-target 66`,
a CPU format first in `--formats`, and `~/.local/bin/uv` not `uv`.

Pi is `ai@raspberrypi.local`, repo at `~/fod-robot-cv-poc`.
